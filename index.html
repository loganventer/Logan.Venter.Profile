Agentic Knowledge Engineering

Agentic Knowledge Ingestion and Curation Pipeline

An agentic service that keeps the knowledge behind AI assistants current. On a schedule, it pulls changes from configured sources and hands them to a team of authoring agents
  • An orchestrator runs every mechanical stage in process and calls four single-purpose agents over the A2A protocol, fanning out per document
  • Each agent does exactly one job, such as writing one document for one source page
  • Agents are definitions and not code: a card, a system prompt and a template in a folder, served by one generic host, so adding an agent is adding a folder
  • Authoring is not deterministic, so an unchanged source is never re-authored, which keeps review free of churn
that write a readable corpus. The result passes a fail-closed sensitive-data gate, is chunked, embedded and indexed, and is published as a pull request for human review before the assistant reloads. The architecture
  • One rule shapes the design: reviewable text and the built index go to different places, tied together by one committed pointer, so a reviewer sees exactly which index build matches the text they approved
  • Four source connector types behind one interface, each with its own change signal, so a new kind of source is one class and a config block
  • Tiered PDF extraction that only falls back to OCR for pages the cheaper tiers could not read
  • Screening runs before indexing, because embedding is the expensive step
  • The index carries a fingerprint of its recipe, and an assistant refuses one that does not match what it serves with
  • Index files are verified by hash and signature before they are opened
  • One circuit breaker per dependency, so a failing endpoint or agent degrades the run without stopping it
  • A new assistant is purely a configuration file, with no per-assistant code
keeps every stage replaceable. I architected and designed the service, and a colleague is building it on the agent framework.
